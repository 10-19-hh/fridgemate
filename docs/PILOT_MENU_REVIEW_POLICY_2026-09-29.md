## 1. 정책 선택지와 추천안

PRD v3의 FR-02·FR-03을 따른다. 원문 행·분량·용도를 보존하고, 미확인은 0이 아니며 임의 환산하지 않는다. 20~30개는 작업 목표이지 숫자를 맞추기 위한 승인 기준이 아니다.

| 결정 항목 | 선택지 | 추천안과 근거 |
|---|---|---|
| 검수 등급 | 한 가지 완료 표시 / 근거에 따른 3등급 | `원문 대조 완료(식재료량)` / `편집 조합` / `미검수`로 구분한다. 수량·과정·인분 검증 상태는 등급과 별도로 남긴다. |
| 과정 물 | 전부 제외 / 전부 수량 추정 / 용도·근거에 따라 구분 | 버리는 데침·삶기·불림 물도 원문·준비 확인에서 삭제하지 않는다. 미정량은 숫자 구매량으로 만들지 않고 확인 필요로 남긴다. 음식에 남는 물은 별도 구분하고 알려진 양은 계산한다. |
| 기본 양념 | 무제한 보유 간주 / 일반 정량 재료와 동일 | 알려진 필요량은 배분·부족 계산에 포함한다. 팬트리 보유 체크만으로 충분한 양을 추정하지 않는다. 양이 미확인이면 수량 확인 필요다. |
| 단품 한 끼 | 밥+반찬 세트만 / 주식 포함 단품도 허용 | 원문 기준 인분이 있고 주식이 포함된 밥·면 단품은 한 끼 후보로 허용한다. 반찬을 단독 저녁으로 승격하지 않는다. 개인의 포만감·영양 적정성은 보장하지 않는다. |
| 파일럿 최소 등급 | 모든 투입량 확인 / 식재료량 확인+불확실성 노출 / 편집 조합 포함 | 두 번째를 추천한다. 6개를 조건부 후보로 삼되 미확인 항목은 계속 확인하도록 한다. 첫 번째를 선택하면 현재 통과는 0개다. 편집 16개는 새 추천에서 제외한다. |

### 등급 정의

1. **원문 대조 완료(식재료량)**: 출처 ID·버전·기준 인분과 필수 식재료의 양·단위·조리 상태가 근거에 연결돼 있다. 현재 코드의 `source-quantity-compared`에 해당한다. 직접 조리, 영양, 조리시간, 모든 과정 투입량의 검수까지 뜻하지 않는다.
2. **편집 조합**: 기존 레시피와 밥·반찬 등을 묶은 구성이며 전체 인분·수량의 원문 대조가 끝나지 않았다. 현재 `composition-only` 16개다. 구성 등급이 있고도 수량은 미검수일 수 있다.
3. **미검수**: 위 근거를 확인하지 못한 신규·외부 항목 또는 출처/버전/필수 검증 정보가 부족한 항목이다. 신규 추천에서 제외한다. 현재 22개 중 별도 미검수 등급은 0개이지만, 이것이 22개 수량 검수 완료라는 뜻은 아니다.

### 계산·안내에서 유지할 경계

- **정량 소스 물**: 칠곡석류국수의 소스 물 600g은 식재료 행으로 유지한다. “물은 과정용”이라는 이유로 정량 수요를 없애지 않는다.
- **미정량 과정 물**: 13개 모두 양을 추정하지 않는다. 특히 취사 물과 녹말물은 음식에 남을 수 있으므로 버리는 물로 묶지 않는다. 준비 확인과 구매 수량을 구분하되, 미확인 상태 자체를 삭제하거나 단순 체크로 정량 검증 완료로 바꾸지 않는다.
- **추가 기름·양념**: 조리 단계에는 있지만 원문 수량이 없는 추가 사용량을 0이나 보유 충분으로 처리하지 않는다. 안내를 보존하고 완전 정량 조리로 표시하지 않는다.
- **기본 양념**: 소금·간장·기름도 검증된 양·단위·조리 상태와 호환되는 실제 재고만 정량 배분한다. 미등록은 실제 미보유의 확정이 아니라 구매 또는 보유 확인 필요다.
- **원문 중복 행**: 용도가 다른 원문 행은 보존한다. 계산 시 호환되는 수량만 합산하고 사용 중 재사용된 같은 분량은 중복 계상하지 않는다.
- **기존 코드와의 구분**: `mealPlanAllocation.js`는 현재 미정량 `processInputs`를 확인 필요에 포함한다. 정책 문서만으로 이 표시가 해소되거나 현재 조리 가능 상태가 바뀌지 않는다. 안내 분리를 구현할 때 확인 필요·재고 이중 배분 방지 회귀를 유지해야 한다.

- 승인 후 필터는 신규 생성·교체·다시 추천 등 새 후보를 고르는 경로에 일관되게 적용한다. 후보가 부족하면 반복/조건 조정을 안내하고 제외 재료를 몰래 넣거나 편집 조합으로 자동 보충하지 않는다.

- 파일럿 분석 동의 여부로 메뉴 기능을 제한하지 않는다. 빌드/제품의 후보 정책과 분석 참여 동의는 별개다.

## 3. 파일럿 저장·회수 운영안

- 앱은 게스트 local-only로 운영하고 파일럿 기록은 별도 동의를 받은 브라우저에 보관한다. 서버 인증·RLS·Hyperdrive 검증 완료로 해석하지 않는다.
- 사용자가 JSON을 직접 내보내어 전달한다. 자동 전송은 하지 않는다. 권장 회수 시점은 주 1회와 마지막 주 종료 시점이며, 전달 채널·담당자·내보낸 사본의 보관/삭제 기간은 모집 전에 별도 확정한다.
- 앱 안의 파일럿 기록은 기존 합의대로 시작 후 35일을 기준으로 다음 실행 시 정리한다. 닫힌 브라우저나 다른 origin의 물리적 삭제를 보장하지 않는다. 내려받아 전달한 JSON 사본은 앱 내 철회·만료로 삭제되지 않으므로 별도 회수 정책이 필요하다.
- 참가 기간에는 **동일 HTTPS origin·브라우저·프로필**을 사용하도록 안내한다. 배포마다 고유 URL을 배포하거나 새 주소로 이동하면 IndexedDB·동의·파일럿 식별자가 나뉜다. 새 주소에서 옛 주소의 데이터를 삭제할 수 없다.
- 내보내기 식별자는 브라우저 범위다. 여러 파일·기기를 고유 사람/계정 수로 합산하지 않는다. 기록 저장만 실패하면 조리·입고는 보존하고 분석 누락을 표시한다.

4. `vercel.json`은 모든 `*.vercel.app` 호스트를 운영 도메인으로 영구 리다이렉트한다. 이전 공개 검사에서 `/about`의 308을 확인한 기록은 [출시 마감 기록](RELEASE_CLOSEOUT_2026-09-29.md)에 있다. 이번에는 HTTP 스모크를 새로 실행하지 않았다.
5. `backendConfig.js`의 실제 동작은 `VITE_API_URL_OVERRIDE` → `VITE_API_URL` → `VITE_API_BASE_URL` 순이다. `*.vercel.app`에서는 API를 비활성화하지만, 운영/www 호스트에서는 값이 모두 비어도 운영 API 기본값을 사용한다. 따라서 운영 `/pilot` 안내만으로 local-only가 되지 않는다.
6. 원격 설정 화면에는 `VITE_API_URL`이 All Environments, `VITE_SENTRY_DSN`이 Production and Preview 범위로 등록돼 있다. 값의 내용·유효성은 확인하지 않았다. Preview를 이미 계측 없는 환경이라고 가정하면 안 된다.

설정대로라면 main 병합 후 Production 배포 및 운영 도메인 연결이 자동 진행된다. 빌드 실패 등으로 실제 반영이 중단될 수는 있지만, **운영 배포가 없는 코드 병합으로 취급하면 안 된다.** 공식 [Vercel Git 배포 설명](https://vercel.com/docs/git#production-branch)도 같은 구조를 설명한다.

### 경로 비교

| 경로 | 판정 | 남은 조건 |
|---|---|---|
| 고정 Preview 브랜치 URL | 우선 추천 | 광범위 리다이렉트 범위를 수정하고 비운영 빌드·헤더·접속 정책을 검증한다. 참가 중 브랜치 URL을 유지하고 검증된 버전만 업데이트한다. |
| 운영 도메인의 `/pilot` | 현재 비추천 | 같은 origin의 기존 저장소와 운영 API 기본값을 공유한다. local-only 분리와 업그레이드·롤백 검증 없이는 빠른 대안이 아니다. |
| 파일럿 전용 하위 도메인 | 대안 | 별도 origin은 확보되지만 API/계측 설정까지 자동 격리되지는 않는다. DNS·도메인 연결과 빌드 환경을 별도로 승인·검증한다. |

Vercel의 브랜치 URL은 새 커밋 이후에도 같은 주소로 최신 브랜치 배포를 가리킨다. 커밋별 고유 URL과 다르다. 실제 할당 URL을 확인해서 사용하고 문자열로 추정하지 않는다. [공식 Generated URLs 문서](https://vercel.com/docs/deployments/generated-urls)

참가 브랜치에 push하면 참가 주소도 새 배포로 바뀔 수 있다. 따라서 별도 검증 브랜치/배포에서 먼저 시험한 뒤 고정 참가 브랜치로 승격하는 절차 또는 동등한 업데이트 통제를 모집 전에 정한다. 현재 그런 배포 차단 장치나 승격 절차가 구현·검증됐다는 뜻은 아니다.

### 모집 전 배포 통과 기준

- main 병합 전에 비운영 대상에서 정책 적용 빌드를 검증한다. 운영 자동 배포/도메인 설정을 임의로 끄거나 바꾸지 않는다.
- 고정 참가 URL의 `/pilot`, `/meal-plan`, `/ingredients`, `/import`, 공개 안내와 새로고침이 **운영으로 이동하지 않고** 해당 빌드에서 열린다. 없는 경로는 실제 404이며 Preview 전체의 색인 차단도 확인한다. noindex는 접근 통제가 아니다. 필요한 참가자 접근 방식은 따로 정하고 기존 Deployment Protection을 임의로 해제하지 않는다.
- 다음 값은 **적용할 목표값**이지 현재 원격 환경 검증 결과가 아니다. Preview 전용 범위에서 세 API 값을 모두 빈 값으로 고정하고 새 빌드를 만든다. `VITE_ADSENSE_VERIFICATION_ENABLED=false`, `VITE_ADSENSE_SERVING_ENABLED=false`, `VITE_GA_MEASUREMENT_ID=`, `VITE_SENTRY_DSN=`, `VITE_ENABLE_EXTERNAL_AI_DATA_PROCESSING=false`, `VITE_ENABLE_REMOTE_IMPORT_LEARNING=false`도 명시한다. 로컬 OCR 자체는 유지한다.
- Sentry는 DSN이 있으면 앱 진입 시 초기화된다. 광고 verification은 legacy enabled 값으로 대체될 수 있으므로 명시적인 false가 필요하다. env 설정은 네트워크 차단 장치가 아니므로 배포 CSP와 실제 요청도 확인한다. 정적 자산·레시피 이미지 요청까지 없는 완전 오프라인을 뜻하지 않는다.
- 새 테스트 브라우저에서 재고 직접 등록 → 식단 생성/확정 → 장보기 → 입고 → 조리 → JSON 내보내기까지 점검한다. 운영 API·인증·외부 AI·GA·Sentry로 데이터가 전송되지 않는지 확인하고 실제 사용자 데이터는 fixture로 쓰지 않는다.
- 동일 origin에서 이전 파일럿 빌드의 합성 데이터를 만든 뒤 업데이트·재실행·롤백 시 보존을 확인한다. **코드 롤백이 IndexedDB 데이터를 자동 복구하지는 않는다.**
- 개발 서버 E2E와 `test:e2e:preview`의 로컬 `vite preview` 통과는 실제 Vercel 라우팅·환경변수·TLS·운영 API 격리 스모크를 대신하지 않는다.

## 5. 승인 후 구현·검증 순서

1. 위 최소 등급과 조건부 후보 6개 허용 여부를 확정한다. 카탈로그 근거/과정 물/기본 양념/원문 행 보존 및 모든 후보 진입 경로의 필터 회귀를 먼저 작성한 뒤 구현한다. 기존 저장 식단의 업그레이드 보호를 포함한다.

## 6. 초안 작성 단계의 작업 범위와 재확인 방법

초안 작성 단계의 신규 파일은 이 문서 하나였다. 그 단계에서는 앱 코드·테스트·설정·원본 루트·환경변수·DNS·배포·원격 PR을 변경하지 않았고 commit/push/merge도 하지 않았다. 문서만 추가했으므로 단위·브라우저 테스트와 build는 재실행하지 않았다. 이전 3,001개 단위/107개 개발 서버 브라우저/48개 빌드 브라우저 결과는 [기존 기록](RELEASE_CLOSEOUT_2026-09-29.md)의 결과이며 초안 작성 단계의 새 실행 결과가 아니다.

확인 대상 소스는 `mealPlanCatalog.js`, `reviewedDinnerCatalog.js`, `reviewedRecipeCatalog.js`, `mealQuantityDomain.js`, `mealPlanAllocation.js`, `backendConfig.js`, `main.jsx`, 광고·분석·외부 AI 설정, 파일럿 저장/내보내기 계약이다. 자료의 비밀값이나 `.env` 내용은 읽지 않았다.
