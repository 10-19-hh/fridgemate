# PRD v3 — OCR 원자 저장과 검토 복구

작업일: 2026-09-28. 전용 작업트리: `prd-v2-recovered-20260919`.
기준 커밋: `b6e3f10480df1cddf9ff005b44f99698befe4c86`.
시작 상태에는 앞선 리팩토링·안정성·AT-18·사용량 정정·첫 진입의 미커밋/미추적
99파일이 포함된다. 이전 `../prd-v3-first-plan-evidence-20260928`은 수정하지 않는다.

## 저장 계약

- 검토한 후보의 ID·시간·필드를 준비 요청에 고정한다. 새 재료에는 허용한 재고 필드만
  복사하며 이미지·OCR 원문·주소·주문번호·보정 제안·임의 메타데이터를 추가하지 않는다.
- 신규 재료 추가, 명시적으로 확인한 기존 재료 교체, 수량 확인 무효화를 기존
  `ingredients`와 `inventoryQuantities`의 한 트랜잭션으로 저장한다. 추가·삭제·마지막
  수량 행까지 성공한 뒤 abort해도 모두 원복되며, commit 전에는 저장 성공을 알리지 않는다.
- 교체 체크 시 대상 전체 행을 복사한다. 재고 재조회로 새 동명 배치가 나타나도 삭제
  대상을 조용히 늘리지 않는다. 메모를 포함한 원본이 바뀌면 오래된 요청을 거절한다.
- 백엔드 연결 계정도 이 단계의 저장은 로컬이다. 새 행에는 pending-create, 교체한 행에는
  내용이 제거된 pending-delete를 사용하며 기존 수동 동기화 경계를 유지한다.
- 동일 준비 요청의 재시도는 기존 행·교체 결과·수량 확인을 검증하고 중복 쓰기 없이
  완료를 확인한다. 이후 수량 확인은 재시도로 무효화하지 않는다. 일부만 존재하거나
  저장된 내용이 수정·삭제됐으면 충돌로 중단한다.
- 완료 확인 뒤에만 보정 학습·선택적 분석·화면 이동을 수행한다. 학습이나 분석 실패가
  완료한 재고 저장을 취소하거나 다시 저장하게 만들지 않는다.

## 화면과 계정 경계

- 저장 중에는 파일·OCR 실행·후보 수정·교체 체크·재고 재확인을 잠근다. 렌더 이전의
  연속 클릭도 동기 잠금으로 막는다. 성공한 요청은 다시 제출하지 않는다.
- 파일 검증·OCR 응답은 해당 파일 세대에만 적용한다. 계정 변경 시 이미지·원문·후보를
  비우고, 이전 계정의 늦은 응답이 학습·원격 요청·분석·이동을 일으키지 않게 한다.
- DB 저장 뒤 응답이 늦은 사이 A→B→A로 돌아와도 기존 목록 캐시 대신 저장소를 읽는다.
  삭제된 계정 캐시를 늦은 완료 응답으로 다시 만들지 않는다.
- ‘재고 다시 확인’은 편집한 후보와 선택을 보존한다. 일반 교체 충돌에서는 이전 교체
  승인과 준비 요청을 버리고 최신 재고를 보고 다시 확인하게 한다. 재조회 실패는
  후보를 지우지 않으며 성공으로 안내하지 않는다.
- 저장 응답만 유실된 뒤 재조회에서 이전 요청 ID가 발견되면 새 저장을 만들지 않고
  ‘이전 저장 결과 다시 확인’으로 안내한다. 후보 수정은 잠그고 원래 요청으로 저장소의
  전체 비교를 다시 통과해야 한다. ID 일치만으로 성공 처리하지 않으며 부분 삭제·수정은
  계속 충돌이다. 새 사진 선택은 명시적인 새 검토이며 기존 재고를 삭제하지 않는다.
- 일반 재고 조회에도 계정 세대·캐시 인스턴스·최신 요청 검사를 적용한다. 오래된 조회가
  새 계정의 오류/로딩을 바꾸거나 삭제된 목록을 복원하지 못한다. 공유 조회의 소유자가
  종료되면 유효한 남은 화면은 이전 스냅샷 대신 새 읽기로 복구한다. CRUD/push/pull의
  요청 정책과 DB 스키마는 바꾸지 않는다.
- 모바일에서도 ‘기존 N개 항목 삭제 후 가져오기’를 생략하지 않고 표시한다. 기존
  색상·타이포그래피와 경고 영역을 유지하고 체크박스의 전체 너비 및 잘림만 고친다.

## 테스트 우선과 중간 실패

착수 시 새 전체 실행은 **206파일 / 2,537개 통과**였다. 이전 완료 보관본의 99파일
해시도 일치했다. 다른 작업트리는 실행 대상에서 제외한다.

- 저장소 API 부재의 assertion 36개 실패를 먼저 확인했다. 이후 원자 롤백·동시/동일 요청·
  전체 원본 충돌·교차 ID·오래된 계정·삭제 표식·입력 복사·민감 정보 비노출 등을 검사한다.
  추가 scope/sparse/배열 own-key RED를 포함해 저장소 집중 검사 46개가 통과했다.
- hook의 최초 `hook-red-01`은 없는 모듈을 Vite가 수집하다 실패한 실행환경/준비 오류다.
  재현 성공으로 세지 않는다. `hook-red-02/03`의 API 부재 assertion을 유효 RED로 보존한다.
  후속 A→B→A 늦은 응답의 실제 화면/DB 불일치를 `hook-aba-red-04`로 확인하고 수정했다.
- 화면은 실제 Provider와 IndexedDB를 사용하며 비싼 인식 및 외부 전송만 대체한다.
  파일/계정 전환·저장 잠금·교체 승인·부수효과 등의 RED와, 재고 재확인 경로의 RED를
  보존했다. 초기에 `put`만 실패시킨 fixture는 실제 신규 경로인 `add`도 검사하도록
  바로잡았으며 이를 제품 코드 수정 근거로 삼지 않았다.
- 최초 전체 `final-unit-01`은 **2,598통과 / 13실패**였다. 신규 화면 테스트 하나의
  5초 타임아웃과 이후 빈 DOM 실패를 통과로 합산하지 않는다. 초기 재고 읽기를 늦추면
  기존 helper가 존재하지만 비활성인 저장 버튼을 클릭해 commit이 0회이고, 무기한
  `act`가 남는 것을 별도의 assertion으로 재현했다. helper는 정상 저장에서 enabled까지
  기다리고, 완료 대기는 제한된 waitFor와 finally 해제를 사용한다. 오류·로딩을 검사하는
  사례에서는 명시적으로 비활성 상태를 검증한다. 테스트 제한 시간은 늘리지 않았다.
- 후속 읽기 검토에서 재조회와 계정 전환/응답 유실의 조합을 발견했다. 재조회 5개 RED는
  실제 오류·캐시·목록·로딩 차이였으며 수정 후 기존 회귀와 함께 통과했다. 공유 읽기
  단순화 중 다른 Provider 갱신이 빠진 중간 회귀는 원래 제품 결함과 구분해 기록하고
  복구했다. 소유자 종료 후 남은 Provider의 로딩 정지도 별도 RED 뒤 수정했다.
- 응답 유실 후 시각을 1분 진행하고 재조회하는 두 사례(교체 있음/없음)는 이전 ID에
  새 시각을 붙인 요청의 충돌을 재현했다. 원래 요청 유지와 별도 재확인으로 수정했다.
  선택 실행의 pending은 필터로 제외한 사례이며 최종 전체 실행의 skip으로 숨기지 않는다.
- 후속 부분 누락/수정 검사의 `ui-followup-green-05` 2실패는 두 줄의 OCR fixture가 실제
  파서에서 한 후보가 된 입력 오류였다. 기존에 검증한 두 상품 영수증 형식으로 바꿨으며
  파서·저장 동작·실패 기대값을 바꾸지 않았다. 이 검사는 GREEN 뒤 추가 경계 검증이고
  원래 제품의 RED로 세지 않는다. 화면 26개는 이후 두 차례 모두 통과했다.
- 최초 새 브라우저 3개는 통과했다. 이후 원복 검사를 마지막 수량 쓰기의 success 뒤
  abort로 강화했다. 모바일 문구 검사는 실제 147px 텍스트가 94px 영역에서 잘리는
  assertion 실패를 확인한 뒤 수정해 통과했다. 이름만 검사하거나 CSS 문자열을 비교한
  것이 아니라 실제 렌더 크기로 확인했다.

## 변경 파일과 재현

이번 단계는 구현 6파일(`ingredientImportRepository`, `ingredientsActions`, `useIngredients`,
`ImportPage`, `UploadBox`, `ParsedItemEditor`), 단위/통합 검사 4파일, 브라우저 1파일,
문서 3파일로 **14파일**이다. 앞선 작업을 포함한 미커밋/미추적 소스·문서는 108파일이다.
이전 99파일 중 의도적인 5개 겹침(README·CHANGELOG·OCR 브라우저·ImportPage·기존
storage 검사) 외의 94개는 내용이 같다. 원본 루트는 변경 목록 해시로 대조하며,
이를 원본 모든 파일의 내용 해시 검사라고 표현하지 않는다.

실행 명령은 아래와 같으며 전용 작업트리에서 수행한다. 단위 검사와 빌드가 끝난 뒤
브라우저 검사를 별도로 실행한다. 최초 브라우저 전체 실행의 자동 권한 검토 시간 초과는
프로세스가 시작되지 않은 환경 문제이며 테스트 실패로 세지 않는다.

submission' --project=local-only --workers=1`을 지정했다. 결과 파일은 실행마다 구분했다.

영구 보관 대상은 `../prd-v3-ocr-evidence-20260928`이다. source manifest·archive·tracked
patch, 이전 99파일 archive/manifest/patch, RED·중간·최종 JSON과 로그, 실패 아티팩트,
모바일 이미지, 실행 목록과 최종 코드 해시 대조를 보관한다. `.env`·비밀키 파일·사용자 DB·
의존성을 포함하지 않는다. 이전 보관본은 그대로 둔다.

복원할 때는 위 기준 커밋의 **새 checkout**에 시작 상태 archive 또는 완료 상태 archive

않고 두 archive를 겹치지 않는다. Node 24와 설치 의존성은 별도로 준비해야 한다.
이번 단계에서는 복원·reset·clean·stash를 실행하지 않는다.

## 보장하지 않는 것과 남은 목표

- 같은 준비 요청의 재시도 보장이지 같은 사진을 새로 인식한 별도 요청의 전역 중복
  제거가 아니다. DB 스키마나 영구 import ledger는 추가하지 않았다.
- 계정 전체 삭제로 수량 revision 표식까지 없어지면 임의의 과거 요청을 DB만으로
  판별할 수 없다. 현재 화면의 계정/캐시 세대 보호와 영구 exactly-once를 구분한다.
- 이미 완료된 DB 쓰기와 이미 서버에 도착한 선택적 원격 학습 요청을 계정 전환으로
  되돌린다는 보장은 없다. 실제 원격 학습/API/운영 DB 호출은 검증하지 않는다.
- 원문량 ‘2팩’을 중량으로 추정하지 않는다. 브라우저 OCR 인식은 테스트 결과로
  대체했으며 실제 영수증 인식 품질이나 인식기의 자동 수량 추출 성능 검사가 아니다.
- 기존 로컬 의존성과 Node 24.19.0, Chromium local-only/API-mock 검증이다. 깨끗한 설치
  CI·실기기·모든 브라우저·전체 접근성/성능·운영 배포 검증이 아니며 React act 경고는
  별도로 남긴다. 테스트 삭제·skip·재시도나 제한 시간 증가로 실패를 숨기지 않는다.
- 손상 보정 데이터의 사용자 복구 UI, 파일럿 별도 동의·수집·지속적 관측 누락·수동
  다운로드, 메뉴 20~30개 검수, 추가 저장 실패 QA, 실제 10~20명/4주 파일럿이 남는다.
