# PRD v3 — 손상된 OCR 보정 기록의 명시적 초기화

작업일: 2026-09-28. 전용 작업트리: `prd-v2-recovered-20260919`.
기준 커밋: `b6e3f10480df1cddf9ff005b44f99698befe4c86`.
시작 상태는 이전 리팩토링·안정성·식단·OCR 작업의 미커밋/미추적 108파일을 포함한다.
`../prd-v3-ocr-evidence-20260928`의 108개 내용 해시가 일치함을 확인하고, 이전 보관본은
수정하지 않는다. 원본 루트를 실행·편집 대상으로 바꾸지 않는다.

## 사용자에게 제공하는 복구 범위

손상된 보정 기록의 일부를 추측해 복원하거나 자동 삭제하지 않는다. 사용자가 사진 등록
화면에서 **보정 기록 초기화 → 초기화 확인**을 선택하면 이 브라우저의 현재 게스트 또는
현재 계정 보정 기록만 지운다. 손상된 일부뿐 아니라 그 범위의 정상 행도 함께 지우는
초기화이며 되돌릴 수 없음을 확인 전에 알린다. 게스트는 이전 버전의 보정 키도 포함한다.

- 취소하면 저장소에 쓰지 않는다. 실제 재고, 수량 확인, 식단과 이력은 삭제하지 않는다.
- 후보 이름·수량·선택·기존 재고 교체 승인과 이전 저장 요청은 유지한다. 초기화 후 현재
  후보를 자동 재인식하거나 과거 보정 전 값으로 되돌리지 않는다.
- 재고 저장 성공 뒤 보정 학습만 실패한 경우에도 초기화할 수 있다. 이미 저장한 재료를
  다시 제출하게 만들지 않으며, 보정 초기화 자체가 새 학습이나 서버 요청을 만들지 않는다.
- 다음번 성공한 재료 저장부터 기존 방식으로 새 보정을 학습한다. 서버에 이미 저장된
  보정 기록을 삭제하는 기능은 아니다.
- 저장소에 접근할 수 없는 상태와 읽을 수 있지만 손상된 상태를 구분한다. 정상 자료의
  저장 용량 부족을 삭제로 해결한다고 권하지 않는다. 읽기 정상은 쓰기 성공 보장이 아니다.
- 확인 중 계정 전환·관련 다른 탭 변경·포커스 복귀는 이전 확인을 폐기한다. 같은 탭에서
  알림 없이 바뀐 값도 실제 삭제 직전 대조한다. 바뀐 자료를 이전 확인으로 지우지 않는다.
- OCR·재고 저장·재조회 중에는 초기화를 막는다. 완료/실패 안내는 별도 복구 영역에 두고,
  취소 후 초기화 버튼, 처리 후 상태 재확인 버튼으로 키보드 초점을 돌린다.

## 저장 계약

`inspectImportCorrections(scope)`는 읽기 전용이다. 기존 JSON 구조·부분 legacy 행 허용
규칙과 v2 우선순위를 그대로 사용한다. `ready`, `damaged`, `unavailable`만 노출하며
손상된 경우에만 확인 토큰을 발급한다. 원문·재료 이름·예외 상세는 토큰이나 UI에 노출하지
않는다. 토큰은 속성이 없는 동결 객체이고 원문 비교값은 모듈 내부 WeakMap에 보관한다.

`resetImportCorrections({ scope, resetToken }, { isCurrent })`는 토큰을 첫 시도에 소모한다.
위조·재사용·다른 범위 토큰을 거부하고, 현재 값과 확인 당시 값의 완전 일치를 확인한다.
게스트에서는 **legacy 삭제·재조회 → v2 삭제·재조회** 순서로 실행해 legacy 삭제 실패 후
옛 보정이 되살아나는 상황을 막는다. 각 삭제 직전에 scope guard와 두 키의 값을 확인한다.
기존 계정 자료 삭제용 `clearImportCorrections`의 호출 계약은 바꾸지 않는다.

| 결과 | 의미 |
| --- | --- |
| `reset` | 최종 재조회에서 대상 키가 모두 없음을 확인 |
| `changed` | 상태/원문이 바뀌어 삭제하지 않음 |
| `invalid` | 확인 토큰·범위·호출 인자가 유효하지 않음 |
| `unavailable` | 삭제 완료를 확인하기 전 저장소 접근 또는 삭제가 실패 |
| `partial` | 일부 삭제됐거나 삭제 시도 후 결과를 전부 확인할 수 없음 |

실패 시 자동 재시도하지 않고 상태 재확인과 새 확인을 요구한다. 지운 원문을 자동으로
다시 쓰지 않는다. 그런 롤백은 다른 탭의 새 기록을 덮어쓸 수 있기 때문이다.

**localStorage의 여러 키 읽기·삭제는 원자적 트랜잭션이나 CAS가 아니다.** 확인 직후 다른
탭이 쓰는 마지막 경쟁, 원문이 A→B→A로 바뀐 이력, 이미 완료된 삭제의 취소를 보장하지
않는다. UI에서도 다른 OCR 탭을 닫고 진행하도록 안내한다. 엄격한 다중 탭 쓰기 직렬화는
모든 학습 쓰기 경로의 협력 또는 별도 저장소 이전이 필요하며 이번 범위가 아니다.

## 테스트 우선과 검증 기록

착수 시 전체 **209파일 / 2,621개**가 새로 통과했다(`baseline-02.json`). 다른 작업트리를
제외하고 기존 설치 의존성과 Node 24.19.0을 사용했다.

- utility 최초 RED는 API 부재 assertion 51개이며 import/실행환경 오류가 아니다.
- 추가 RED는 snapshot 읽기 도중 guard가 바뀐 뒤 삭제되는 경우다. 실제 삭제 직전
  guard를 다시 확인하도록 수정한다. 정상 apply/save/clear와 부분 legacy 행은 유지한다.
- UI 최초 `ui-red-01` 중 식단 fixture의 저장 revision 누락은 준비 오류로 구분한다.
  이를 수정한 `ui-red-02`는 정상 읽기+quota 보호 1통과, 복구 영역 부재 14실패다.
- 브라우저 최초 실행은 없는 복구 버튼 대기에서 3개가 시간 초과했다. 명시적 화면
  assertion을 추가한 `browser-red-02`는 세 사례 모두 복구 영역 부재로 실패했다.
  이후 조작할 수 없는 화면에서 실패한 것이며 환경/import 오류를 RED로 세지 않는다.
- `ui-green-03`은 이름과 달리 13통과/2실패다. 접근 불가 설명의 ‘손상 여부는 미확인’을
  손상 확정으로 오인한 테스트 정규식을 좁혔다. 또한 새 재고 저장이 끝나면 학습 쓰기를
  시도하므로 이전 초기화 확인을 폐기하고 새 확인을 요구하는 경계를 검사하도록 바꿨다.
  진행 중 동기 차단·원문 보존·저장 완료 잠금 검사는 그대로 유지했다.
- 초기화 후 다른 탭에서 손상된 새 기록이 생겨도 과거 성공 문구가 남는 실제 결함을
  `ui-message-red-05`로 확인한 뒤 외부 재검사에서 과거 결과 안내를 지우도록 고쳤다.
  단독 선택 실행의 제외 15개는 최종 전체 검사의 skip으로 합산하지 않는다.
- 후속 검사로 legacy만 손상된 경우, 점검 후 접근 차단, 저장 응답 유실→재고 재조회→
  보정 초기화→같은 요청 재확인을 추가했다. 이들은 GREEN 후 보강이며 원래 결함의
  RED라고 주장하지 않는다. 유틸 신규 59+기존 34, 화면 신규 17+기존 26이 각각 통과했다.
- 첫 새 브라우저 GREEN은 3개 통과지만 실행 중 UI HMR이 있었으므로 최종 결과로
  쓰지 않는다. 이후 코드 파일 해시를 고정한 상태에서 전체 검사를 다시 실행한다.

최종 전체 단위·통합은 **211파일 / 2,697개 통과**, 실패·skip·todo 0이다. 시작의 2,621개를
유지하고 76개를 추가했다. 린트·빌드·diff 검사를 통과했고 빌드는 공개 경로 113개와
사이트맵·noindex 앱 셸을 확인했다.

최종 전체 브라우저 **75개 통과**(기존 72+신규 3), skip·flaky·자동 재시도 0이다. 확인 취소와
실제 식단/재고/편집 보존, 초기화 후 새 학습, 실제 두 번째 탭 변경, legacy 삭제 실패와
명시 재시도를 검사했다. 390px 확인/실패 화면에서 안내·버튼의 줄바꿈과 가로 넘침 없음을
검사하고 이미지를 직접 확인했다. 전체 접근성 감사나 실제 모바일 기기 검증은 아니다.

최종 단위·브라우저 실행 전 고정한 **코드·테스트 101파일**의 해시가 끝까지 일치한다.
검사 이름과 실제 실행 경로를 대조해 기존 검사 삭제나 다른 작업트리 혼입이 없음을 확인한다.
기존 서버 테스트 한 개의 이름에 들어가는 실행 시각만 이전과 동일하게 정규화해 대조하며
그 테스트 소스는 변경하지 않았다. 기존 React `act` 경고와 브라우저 색상 환경 경고는 남는다.

테스트 우선 스킬은 API/화면 부재와 후속 오류를 실제 실패로 확인하는 데 적용했다. React
가이드는 삭제를 이벤트 핸들러에서만 수행하고 확인 토큰·동기 guard를 ref로 관리하는 데,
디자인 가이드는 기존 색상·폰트를 유지한 인라인 확인과 초점·모바일 가독성 검토에 적용했다.

파서·검토·localStorage·IndexedDB·식단 저장은 실제 코드로 검사한다.

이번 단계 변경은 구현 3파일(`importLearning`, `ImportCorrectionRecoveryPanel`, `ImportPage`),
새 단위/화면 검사 2파일, 브라우저 1파일, 문서 3파일로 **9파일**이다. 누적 미커밋/미추적
소스는 **112파일**이며, 앞선 108개 중 의도적인 5개 겹침(README·CHANGELOG·OCR 브라우저·
ImportPage·importLearning) 외의 103개는 내용이 같다. 원본 루트의 변경 목록 해시도 이전과
동일함을 확인하며, 이를 원본 모든 파일 내용까지 해시 대조했다는 뜻으로 확대하지 않는다.

작업 증거의 임시 경로는 `/private/tmp/fridgemate-correction-recovery-jYuSyty4`다.
인접 `../prd-v3-correction-recovery-evidence-20260928`에 시작/완료 소스 archive·manifest·
tracked patch·실패/최종 JSON·로그·모바일 화면을 보존한다. 비밀키·`.env`·사용자 DB·의존성은
포함하지 않는다. 복원은 기준 커밋의 **새 checkout**에 시작 또는 완료 archive 하나를 풀고
해시를 대조하는 방식이다. 두 archive를 겹치거나 현재 작업트리/원본 루트에 덮어쓰지 않는다.
Node 24와 기존 의존성 환경은 별도로 준비해야 한다.

## 남은 전체 목표와 제한

이번 변경은 손상된 로컬 보정의 사용자 초기화다. 임의의 원문 복원·서버 보정 삭제·새 OCR
인식 품질 개선·브라우저 간 동기화·저장소 이전·DB 스키마 변경은 아니다. 실제 기기·운영
API·깨끗한 설치 CI를 검증했다고 주장하지 않는다.

이후 파일럿 별도 동의/철회 화면·실제 수집·지속적 관측 누락·수동 다운로드 연결, 메뉴
20~30개 검수, 추가 저장 실패·실기기·접근성·성능 QA와 10~20명/4주 파일럿이 남는다.
로컬 보관·수동 내보내기·35일 후 다음 실행 정리·분석 실패에도 조리/입고 보존은 유지한다.
공개 소개·검색 유입 관측과 후속 예산·선호·공유 등 전체 PRD 범위를 줄이지 않는다.
원본 루트·보관본 수정, commit/push/PR/병합/배포/참여자 모집은 수행하지 않는다.
