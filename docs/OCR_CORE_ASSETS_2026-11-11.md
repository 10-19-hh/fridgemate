# OCR 코어 누락 수정과 실제 실행 검증

기록 기준일: 2026-11-11 KST. `origin/main`의 `aa2679df8859305283c9adebfbcbba54713812d1`에서 분리한 `codex/fix-ocr-core-assets` 작업이다. 배포·운영 복구 완료 기록이 아니다.

## 원인과 수정 범위

2026-11-09 배포 Chromium 감사에서 가상 주문 이미지의 인식이 시작되지 않았고, `/ocr/tesseract/core/tesseract-core-relaxedsimd-lstm.wasm.js`의 404 및 worker의 `importScripts` 오류가 확인됐다. 관찰한 브라우저의 실패이며 모든 사용자·브라우저의 실패를 입증하지 않는다.

설치된 Tesseract.js/core 7.0.0의 브라우저 로더는 relaxed SIMD, SIMD, 기본 코어와 LSTM 여부에 따라 여섯 변형 중 하나를 선택한다. 복사 스크립트에는 네 변형만 있었다. 다음 두 파일을 추가했다.

- `tesseract-core-relaxedsimd.wasm.js`
- `tesseract-core-relaxedsimd-lstm.wasm.js`

이제 worker 1개, core 6개, 언어 2개를 복사한다. 일반·파일럿 출력 모두 같은 계약을 검사한다. 앱 UI·인식 파라미터·재료 파서·DB·홈은 변경하지 않았고 의존성도 추가하지 않았다. 과거 문서의 ‘7개 복사 성공’은 당시 사실이므로 소급해서 숫자를 바꾸지 않는다.

## 검사가 증명하는 범위

- `scripts/__tests__/tesseract-assets.test.js`: 실제 복사 스크립트를 임시 디렉터리에서 실행하고 일반/파일럿 출력의 여섯 코어, worker, 언어 파일을 설치 원본과 바이트 단위로 비교한다. 파일 개수나 소스 문자열만 확인하지 않는다.
- `e2e/ocr-real.spec.js`: 새 게스트 context에서 일반 빌드의 실제 엔진으로 고정 PNG `계란 10개`를 읽는다. 후보 `계란`, 검토 전 재고 없음, `유정란`으로 수정 후 저장, 새로고침 후 보존을 확인한다. 인식 override나 가짜 네트워크 응답은 없다.
- 모든 OCR 자산을 직접 GET하여 성공·본문·유형을 확인한다. 리다이렉트는 따라가지 않는다. 브라우저가 보고한 실제 요청은 별도로 첨부하며, 관측되지 않은 worker 응답을 실제 요청 기록으로 만들어 넣지 않는다. 언어 파일은 HTTP 압축 해제 때문에 응답의 gzip 마커를 강제하지 않고 실제 엔진 로딩으로도 확인한다.
- 외부 origin 및 GET/HEAD 이외 브라우저 요청을 차단한다. 로그인을 하지 않고 저장은 새 context의 게스트 IndexedDB에만 한다. 차단된 공공 레시피 이미지 요청은 증거 JSON에 남는다.
- 기존 `e2e/ocr-import.spec.js`는 인식 결과를 대체해 검토·편집·저장을 검사하며 유지한다. 기존 공개 배포 검사는 HTML·메타·구조화 데이터·사이트맵 등도 확인하지만 OCR 실행을 포함하지 않았다. ‘페이지 200만 검사했다’고 축약하지 않는다.
- `playwright.preview.config.js`에 실제 OCR spec을 추가했다. 기존 CI의 일반 빌드 Chromium 검사에 포함된다. 아래 결과는 PR 제출 전 로컬 검증이며, 원격 CI·배포 결과는 별도로 확인한다.

## 실행 결과와 중간 실패

1. 수정 전 자산 검사: 일반·파일럿 모두 relaxed 코어 두 개 누락으로 실패했다.
2. 수정 전 일반 빌드 실제 Chromium: 화면의 ‘사진을 읽는 데 실패했어요’로 실패했다. 당시 빌드는 자산 7개만 복사했다.
3. 수정 후 자산 검사: 2개 통과. 일반 빌드: 자산 9개 복사, 공개 경로 113개의 빌드 검증 통과.
4. 전체 단위·통합: **243파일 / 3,167개 통과**. lint 통과. Node 24, macOS 환경이다. 이전의 3,165개에 자산 검사 2개가 추가됐다.
5. 실제 OCR 단일 입력: **Chromium·Firefox·WebKit 각 1개, 총 3개 통과**. Chromium의 실제 relaxed SIMD LSTM 요청은 200, WebKit의 SIMD LSTM 요청도 200이었다. Firefox에서는 worker/core 요청이 자동화 응답 이벤트에 나타나지 않아 선택 코어를 확정하지 않는다. 세 엔진 모두 자산 직접 조회와 실제 인식·저장 검사를 통과했다.
6. 일반 빌드 preview 전체: **49개 통과**. 기존 48개에 실제 OCR 검사 1개가 추가됐다.

위 검사들은 목적이 겹치므로 합산해서 서로 다른 사용자 사례 수로 표현하지 않는다. WebKit 자동화가 실제 iPhone Safari 검증을 대신하지 않는다.

검사 작성 중에는 압축 해제된 언어 응답에 gzip 마커를 기대하는 잘못된 단정도 실패했다. 이를 바로잡았으며 제품 결함으로 세지 않는다. 후보가 없는 경우를 조기에 실패로 처리하도록 관찰 조건을 보완했다. 아래 입력 품질 실패는 검사 코드 실수와 구분한다.

## 새로 드러난 미해결 품질 문제

코어 로딩이 복구된 뒤에도 다음 입력들은 기대한 재료 후보를 만들지 못했다.

| 가상 입력 | 관찰 결과 |
| --- | --- |
| 기존 감사의 주문내역 표: 계란·두부·대파 | Chromium/Firefox 후보는 `점검용 가상 이미지`만, WebKit은 `가상 장보기 내역`, `대파` |
| 큰 글씨의 계란·두부·대파 세 줄 | 화면 원문에 세 재료가 보이지만 `계란` 한 후보로 묶임 |
| `두부 1모` 한 줄 및 별도 두부 영수증 형태 | 후보 없음 또는 다른 이름으로 오인식 |

따라서 **404 수정은 사진 등록 품질 전반의 해결이 아니다.** 최종 자동 smoke는 알려진 단일 계란 입력의 엔진·저장 연결만 확인한다. 기대한 세 재료를 한 재료로 바꿔 성공했다고 보고하지 않는다. 표·여러 줄 실패 이미지와 범위는 `e2e/fixtures/OCR_FIXTURES.md`에 보존했다. 파서의 여러 상품 분리와 원문 인식 품질은 후속 수정 대상으로 남긴다.

실제 영수증·주문 캡처 10~20장, 수정률·누락률·오탐률, iPhone 실기기, 실제 배포 후 인식은 미검증이다. 사진 입력 성공을 전제로 한 참여자 점검·시연은 이 문제와 실제 배포를 재확인한 뒤 진행해야 한다.

## 실행 방법

Node 24와 잠금 파일 의존성을 사용한다. 일반 빌드이며 `VITE_LOCAL_PILOT_ENABLED`를 설정하지 않는다. 로컬 검사는 API·분석 설정이 없는 환경에서 실행한다.

```sh
npm ci
npx playwright install chromium firefox webkit
npm run test:run
npm run lint
npm run build
npm run test:e2e:ocr
npm run test:e2e:preview
```

실제 배포 후에는 다음과 같이 같은 검사를 명시적으로 운영 주소에 실행할 수 있다. 아래 명령을 이 작업에서 실행했다는 뜻은 아니다.

```sh
OCR_SMOKE_BASE_URL=https://xn--wh1bs8l5xa003adme.com npm run test:e2e:ocr -- --project=chromium
```

추가 엔진은 `--project=firefox`, `--project=webkit`으로 선택한다. 증거는 `test-results/ocr/*/ocr-network-evidence.json`, 실패 시 스크린샷·trace에 남는다. 운영 서버에 데이터를 쓰지 않지만 테스트용 새 게스트 저장소에는 가상 재료를 저장한다. 이 기록의 로컬 검사 통과는 PR 병합이나 운영 배포 후 복구를 뜻하지 않는다.
