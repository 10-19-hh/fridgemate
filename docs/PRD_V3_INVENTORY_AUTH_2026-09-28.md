# PRD v3 — 재고 실패 안내와 인증 요청 경계

작업일: 2026-09-28. 전용 작업트리 `prd-v2-recovered-20260919`, 기준 커밋
`b6e3f10480df1cddf9ff005b44f99698befe4c86`. 팬트리·취향 안정화 완료본의
미커밋/미추적 149파일을 포함한 상태에서 이어 작업한다. 원본 루트·앞선 보관본은
수정하지 않으며 의존성·서버 인증 계약·DB·추천 정책은 이 단계의 변경 대상이 아니다.

## 확인한 문제와 변경 계약

- 재고 추가·수정·삭제 실패의 rollback 뒤 오류가 화면 상태로 전달되지 않았다.
  실패를 안전한 문구로 알리고 입력과 기존 재고를 보존하며 재시도를 허용한다.
- 홈·메뉴·재고 목록에서 조회 실패와 정상 빈 재고를 구분한다. 조회를 다시 확인하기
  전에는 재고가 비었다거나 개인화 추천이 확정됐다고 표시하지 않는다. 공개 메뉴 탐색과
  식단 진입은 유지한다.
- 수정 대상의 조회 실패·대상 없음은 서로 구분하고 입력·저장을 잠근다. 명시적
  재조회 성공 뒤에만 편집을 허용한다. 계정·대상 이동 뒤의 이전 조회/저장 응답은
  현재 폼의 입력·안내·화면 이동에 사용하지 않는다.
- 변경 전 계정의 늦은 rollback·조회 결과가 새 계정의 재고/cache/dirty 상태를 덮지
  않도록 한다. 같은 계정에 돌아온 경우도 이전 세션의 연장이 아니다.
- 전체 조회 완료와 단일 행 갱신을 구분한다. 전체 조회 실패 뒤 단건 저장/조회만으로
  부분 목록을 완전한 재고로 표시하지 않는다. OCR 등 전체 snapshot 갱신과 겹친
  이전 조회는 최신 상태를 다시 확인하며, 같은 행의 겹친 수정 실패는 미저장
  optimistic 값이 아니라 마지막 확인된 값으로 정산한다.
- 401 뒤 자동 재인증은 원래 요청의 계정·세션이 유지될 때만 재시도한다. 로그아웃,
  다른 계정 로그인, 같은 계정 재로그인 뒤 이전 payload를 재전송하지 않는다.
  늦은 세션 복구 응답이 로그아웃이나 새 로그인을 되돌리지 않도록 한다.
- 화면에서 만들어진 로그아웃·계정 삭제·guest 가져오기/닫기 콜백의 소유 세션을
  실행 직전에 확인한다. 다른 계정 전환과 같은 계정 재로그인 모두 이전 콜백을
  무효화한다. 일반적인 같은 계정 refresh는 정상 콜백을 무효화하지 않는다.
- 이미 계정을 확인할 수 없다고 판단한 상태에서 재확인 중에는 refresh 통신만
  허용하고 업무 요청은 잠근다. 수동 push/pull도 시작 시점과 로컬 조회·API·cache
  저장의 await 이후에 캡처한 세션을 확인한다. 기존 payload/병합 정책은 유지한다.

## 검증 기록

변경 전 기준선은 Node 24.19.0·기존 설치 의존성에서 **221파일 / 2,818개 통과**,
실패·skip·todo 0이다. 실행 대상에서 `.worktrees/**`를 제외했다.

- `inventory-e2e-red-01`: 전체 Playwright 제목에 맞지 않는 `^inventory` 필터로
  테스트가 수집되지 않았다. 실행 절차 오류이며 기능 RED로 세지 않는다.
- `inventory-e2e-red-02`: 필터 수정 뒤 실제 IndexedDB 읽기/삭제 실패를 주입하여
  홈·메뉴·목록 조회 3건, 삭제 1건, 수정 폼 조회 1건의 안내 부재를 assertion으로 재현했다.
- `auth-e2e-red-01`: 헤더와 본문의 같은 이름 로그아웃 버튼을 구분하지 못한 선택자
  오류다. 계정 화면 본문으로 범위를 좁힌 뒤 다시 실행했다.
- `auth-e2e-red-02`: 실제 앱의 취향 저장을 보류하고 UI에서 로그아웃·재로그인한 뒤
  이전 요청의 401을 반환했다. 다른 계정과 같은 계정 재로그인 모두 PUT 1회 기대와
  실제 2회의 차이로 실패했다. 다른 계정 사례는 이전 계정의 입력이 새 계정으로
  재전송됐다. API 응답과 서버 상태는 가짜이며 운영 계정·DB를 사용하지 않았다.
- 위 실패 재현 및 중간 집중 검사는 아래의 고정 소스 전체 검사와 구분한다.
  테스트 수집·선택자·fixture 오류를 기능 실패 재현으로 세지 않는다.

### 독립 검토에서 추가한 경계

- 수정 폼의 warm-cache A/B 동일 ID 검사는 처음 StrictMode에서 15개 모두 통과했다.
  이 실행은 RED가 아니다. 개발 StrictMode와 단일 effect 실행을 각각 검사한
  `form-warm-scope-modes-07`에서 단일 effect 사례가 B 기대/A 실제로 실패했다.
  scoped cache 접근 수정 뒤 `form-warm-scope-modes-green-08`은 두 모드 포함 16개 통과다.
- `storage-review-red-09`는 정상 보호 21개 통과, 부분 조회를 완료로 취급하는 2개,
  OCR 저장과 이전 조회의 경합 2개, 겹친 수정의 양쪽 실패 2개가 예상 assertion으로
  실패했다. 보강 뒤 `inventory-focused-green-10`은 기존 검사 포함 11파일 96개 통과다.
- 인증의 첫 집중 통과 뒤에도 로그인 응답 본문 대기, storage 이벤트 처리 전 token
  변경, 잘못된 refresh 이후 새 요청, 명시 로그아웃 이후 새 요청을 별도로 재현했다.
  중간 결과 `auth-related-green-02`는 15파일 119개 통과지만 최종 전체 검사는 아니다.
  일부 기존 테스트의 성공 refresh fixture에는 실제 `{user}` 응답과 확인된 계정이
  빠져 있었으며 이를 보강했다. refresh 공유 1회·각 요청 재시도 1회의 기존 기대는 유지한다.
- 추가 독립 검토는 이미 전송된 요청과 별개인 **전송 전 소유 계정**을 다뤘다.
  `auth-owner-red-02`는 정상 보호 31개 통과, 이전 삭제·로그아웃·guest 가져오기/닫기
  콜백 8개, guest 읽기/교체 완료 이후 4개, 재확인 대기 중 업무 발송 1개가
  assertion 차이로 실패했다. 보강 뒤 `auth-related-green-03`은 15파일 133개 통과다.
  인증 범위 신규 테스트는 총 46개다. 중간 9파일 해시와 최종 11파일 해시를 별도로 보관한다.
- `manual-sync-red-11`은 기존 16개 통과, 수동 동기화의 이전 콜백·로컬 조회 중
  계정 전환·늦은 API 응답/저장 ACK 10개가 assertion으로 실패했다.
  `manual-sync-green-12`는 26개 모두 통과했고, 최종 재고 집중 검사
  `inventory-focused-green-13`은 11파일 106개 통과했다.
- 최종 독립 검토는 위 전송 전 경계에 추가 blocker를 발견하지 못했다. 인증 11파일의
  최종 SHA를 재확인했고 수동 동기화의 콜백 연결·await 경계와 실제 결과 파일을 대조했다.
  운영 API 또는 사용자 DB에 요청하지 않았으며 전체 앱의 보안 인증을 뜻하지 않는다.

신규 단위·통합 104개와 브라우저 7개를 추가했다. 보관 검증은 기존 2,818개와 82개의
파일/테스트 이름이 최종 결과에도 모두 존재하는지 확인한다. 단위 실행 대상은 전용
작업트리 아래이며 중첩 `.worktrees/**`가 없다. 브라우저는 11파일에서 각 1회 실행했고
retry·skip·flaky·report error가 없다. 실제 서버 인증/DB 대신 API 모의 응답을 사용한다.
일부 React 테스트의 `act(...)` 경고와 브라우저 실행의 `NO_COLOR` 경고는 남아 있다.
경고가 없는 검사라고 보고하지 않는다. 빌드·린트의 경고/오류 출력은 없었다.

최종 모바일 실패 화면을 직접 확인했다. 재고 확인 불가 안내와 재조회 버튼, 첫 식단
진입 및 공개 메뉴 탐색이 함께 읽힌다. 이것은 특정 화면의 시각 검증이며 전체
접근성 감사·실기기 성능/호환성 검증을 대신하지 않는다.

테스트 우선 절차로 유효한 assertion 실패를 확인한 다음 구현했으며, React 지침에
따라 계정별 폼 생명주기와 오래된 비동기 결과를 분리했다. 디자인 지침은 기존 화면의
문구·경고·복구 버튼을 유지하는 데 적용했고 새로운 시각 체계로 전면 교체하지 않았다.

## 남은 전체 목표와 한계

클라이언트가 이미 전송한 요청이나 브라우저가 적용한 서버 쿠키를 되돌리는 기능은
아니다. 예를 들어 늦은 로그인/refresh 응답의 HttpOnly Set-Cookie가 이미 확인한
B 계정 뒤 쿠키만 A로 바꾸고, 다음 요청이 200을 반환하면 프런트엔드 세대만으로
서버의 실제 처리 계정을 확정할 수 없다. 서버의 예상 계정 검사나 더 넓은 인증
전환 직렬화는 후속 검증이 필요하다. 실제 운영 API와 다중 기기의 계정 격리까지
검증했다고 하지 않는다. storage 접근 불가 시 다른 탭 알림도 최선 노력이며,
refresh 공유는 한 JS 실행 공간 안에서만 적용한다.
이미 시작된 IndexedDB 교체도 이 guard만으로 취소하지 못한다. 교체 이후 guest 결정
기록과 현재 계정 UI의 변경은 차단하지만, 시작된 저장 작업의 롤백을 보장하지 않는다.

메뉴 20~30개 검수, 전체 저장소 장애·실기기·접근성·성능 QA, 새 설치/Linux CI,
운영 검증 및 10~20명/4주 실제 파일럿은 계속 남는다. 공개 소개·검색 유입과 후속
예산·선호 확장·공유·수익화 목표도 유지한다. 커밋·푸시·PR·병합·배포·참여자 모집은
이 단계에서 수행하지 않는다.

실제 전체 실행은 `/private/tmp/fridgemate-inventory-auth-lboIwQZL/run-check.mjs`를
`unit 01`, `lint 01`, `build 01`, `e2e 01` 인자로 각각 호출했다. 위 npm 명령에 JSON

`preserve.mjs freeze 01` 이후의 소스와 결과인지 검사하고 `preserve.mjs archive 01`로
보관한다. 두 스크립트 자체도 검증 자료에 포함한다.

완료 보관 경로는 `../prd-v3-inventory-auth-evidence-20260928`이며 다음을 포함한다.

- `source-files.tar.gz`, `source-manifest.json`: 기존 작업 포함 최종 170파일과 각 SHA-256.
- `tracked.patch`: 기준 HEAD 대비 추적 파일 diff. 미추적 파일은 위 archive에 포함한다.
- `phase-summary.json`: 이번 단계 31파일, 추가 테스트 목록, 원본 루트 상태 목록 해시,
  최종 archive SHA-256 및 archive 내부 170파일 해시 대조 결과.
- `validation/`: 전체/집중 검사·유효 RED 및 절차 오류 기록·코드 고정/보관 스크립트.

복원은 원본/현재 작업트리가 아닌 **새로운 깨끗한 checkout**에서 수행한다.

1. 기준 커밋 `b6e3f10480df1cddf9ff005b44f99698befe4c86`을 checkout한다.
2. 시작 재현이면 `starting149-source-files.tar.gz`, 완료 재현이면 `source-files.tar.gz`
   **하나만** 해당 새 checkout에 푼다. 두 archive를 겹쳐 적용하지 않는다.
3. 대응 manifest의 모든 파일 SHA-256을 대조한다. `tracked.patch`는 검토용이며
   같은 archive 적용 후 다시 적용하지 않는다.
4. 이 검증과 같은 Node 24.19.0 및 기존 의존성 환경을 별도로 준비하고 위 명령을 실행한다.
   의존성은 archive에 없으며 깨끗한 Linux 설치 검증을 했다는 의미가 아니다.

원본 루트의 상태 목록 해시는 작업 시작 때와 동일하다. 상태 목록만으로 모든 파일의
내용 불변을 증명하지는 않으며, 이 단계의 파일 쓰기 대상은 전용 작업트리와 새 증거

검사는 범용 비밀 탐지기가 아니다. 기존 보관본과 변경·미추적 파일은 지우거나 덮지 않았다.
